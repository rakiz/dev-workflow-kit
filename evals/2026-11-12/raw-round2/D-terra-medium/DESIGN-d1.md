# backupctl snapshot design

## Contract and scope

One run produces **one atomic snapshot of all configured directories**, not N independently committed backups. Configuration gives each directory a stable, unique ID and an absolute source path, plus an absolute backup root. IDs and relative paths are validated; sources must be disjoint, and the backup root must not be inside a source. Configuration changes appear in the next snapshot; older snapshots retain their own directory IDs. Run locally on a filesystem that supports same-filesystem atomic directory rename, hard links, advisory locks and directory fsync. Reject unsupported filesystems rather than silently weaken the protocol. Backup files and metadata are immutable after publication; backupctl and readers must not modify them, including through hard links.

**Point-in-time requires source cooperation.** All evals writers must take a shared, per-source writer lock before modifying a source. Backupctl acquires the exclusive side of *all* source locks in stable ID order before scanning any source, and holds them through the last copy and verification. Thus every source is frozen simultaneously and the resulting image represents the instant the last lock was acquired. Locks live outside the source trees and all writers must use the same lock paths. External writers that ignore this protocol cannot be made point-in-time safe by stat-and-copy; detect observable changes and abort, but do not claim a consistent snapshot in their presence. A filesystem snapshot facility could replace this contract, but is not assumed. Locks are OS-managed and released on process death; a sleeping process retains its locks until it resumes or dies.

The image includes regular files, empty directories, and dotfiles and dot-directories. Symlinks and special files are rejected with an actionable error, rather than followed or silently omitted. File contents and relative paths are the restore contract; source ownership, permissions, timestamps, ACLs and hard-link identity are not. Snapshot directories and files are private to the backup user. The index is metadata, not part of restored source contents.

## Existing code and necessary changes

Implementation belongs alongside `synccli.py`; factor shared primitives there, retaining its existing CLI behavior where possible. Do not call `synccli.sync` as the backup transaction.

* Scanning builds on `synccli.scan_files` (`synccli.py:10–19`), which uses `os.walk` and sorted relative names. Extend/refactor its traversal for backup mode to include hidden directories (currently filtered at line 14), record empty directories, report walk/stat errors instead of `os.walk`'s default silent errors, and reject symlinks and non-regular files using no-follow checks. Validate every relative component and never follow a link when opening or creating a path.
* Manifest creation builds on `synccli.build_manifest` and `file_state` (`synccli.py:22–33`). Extend the scanner/manifest interface for per-file errors, directory entries, and explicit source states; currently one failed `stat` aborts without contextual reporting, and `os.stat` follows links. `file_state` supplies the existing `{size, mtime}` source fingerprint, not a content hash. Preserve that representation for comparison.
* Change detection uses `synccli.changed_files` (`synccli.py:36–42`) on the previous and current source-state maps, separately by source ID. Deleted paths are simply absent from the newly assembled tree. An ID newly added to configuration has an empty previous map.
* Copying builds on `synccli.copy_file` (`synccli.py:62–69`), but refactor it to offer a strict streaming mode: bounded chunks, exclusive creation in staging, explicit success/error and byte count, propagated source and destination errors, and cleanup of a partial destination. Its current whole-file `read()` is unbounded, and its swallowed `OSError` can leave a truncated file. Backup mode must never use that behavior. Preserve the old sync caller's compatibility as appropriate.
* Override the in-place publication in `synccli.sync` (`synccli.py:72–87`): it writes directly into the destination, never removes stale files, and writes the source manifest even after a silently failed copy. It neither isolates concurrent runs nor protects readers from a partially written manifest. The backup transaction below uses its shared primitives but constructs and publishes a new immutable tree instead. `collect_stale` (`synccli.py:45–59`) is not a retention or snapshot garbage collector.

## Storage, publication, and concurrency

Under the root, keep persistent lock files, `staging/<unique-id>/`, and `snapshots/<sequence>-<unique-id>/`. An image contains `trees/<source-id>/...` and metadata outside `trees`: a versioned `index.json` mapping source IDs to source fingerprints and relative file paths, a directory list, and a seal containing a digest of the exact index bytes. IDs are restricted safe single components. Index paths must be unique normalized relative paths with no `..`, absolute path, symlink, or file/directory collision. The tree and index contain exactly the same files and directories; validation walks the tree, checks types and file sizes and compares the sets. The seal detects an incomplete or accidentally corrupted index; it is not an authenticity mechanism.

1. A run takes an exclusive **writer lock** for the root, serializing scheduler and manual runs. Both use the same code, configuration, wait behavior, result format and exit statuses. After acquiring it, clean abandoned staging trees; none can be active because every writer holds this lock. Generate an unpredictable unique staging name and a sequence greater than every published sequence under the lock; sequence ordering, not wall-clock time, identifies the latest snapshot.
2. With the writer lock held, take the exclusive **GC lock** to validate published candidates and apply recovery below, then release it. Take the shared GC lock before selecting the newest valid previous image and hold it through publication, protecting all hard-link sources. The writer lock prevents another writer or GC from changing that selection between lock acquisitions. Lock order is writer, then GC, then source locks. Readers take only the shared GC lock; GC takes the writer lock and then the exclusive GC lock. No lock is upgraded in place.
3. Freeze all sources as described above. Scan and build the current manifests. For each regular file, open the source without following links and check it is readable, regular and still matches the scanned state. Compare source states with `changed_files`. For an unchanged entry, hard-link the corresponding validated previous snapshot file into the new staging tree; otherwise stream-copy the source into a newly created file. Never open a prior snapshot file for writing. Recheck source descriptor state after copying, and fail if it changed. Create all directories, including empty ones. Check each resulting file and reconcile the entire staged tree against the planned index. Any error aborts the whole run; no partial success is published.
4. Write `index.json` and the seal only after the tree is complete. Flush and fsync copied files, index and seal; fsync newly populated directories bottom-up, including the staging image directory. Atomically rename the whole image to its final name within the same filesystem, then fsync both the snapshots and staging parent directories. The rename is the sole commit point: readers enumerate only `snapshots/` and never staging. There is no mutable `latest` pointer to get out of sync. Release source and shared GC locks after commit. If an fsync or rename fails, report failure; after a rename followed by an fsync failure the outcome is explicitly **indeterminate**, and the next run validates what is present rather than assuming either outcome.
5. After a successful commit, perform retention under the exclusive GC lock, while still holding the writer lock. Report the snapshot ID, copied/reused file counts and bytes, and any retention failure. A retention failure does not invalidate the committed backup, but makes the command return a distinct nonzero status.

Every restore, next-run reader, and human inspecting a snapshot must acquire the shared GC lock **before listing or choosing a snapshot and hold it until all reads and file handles are finished**. Provide a `backupctl read <id> -- <command>` wrapper for human and restore tooling; it takes the lock, validates the requested image, sets the image path for the command, and waits for it. Direct uncoordinated filesystem reads cannot be protected from deletion, so they are outside the contract. Readers never wait for the producing run to finish: a visible final directory is already committed and immutable. They can read an old image while a new one is built. Exclusive GC may wait for long-running readers; new runs may also wait for GC or source writers. Do not break locks based on age.

## Failure, index recovery, and reporting

The process may die between any operations. Before rename only an untrusted staging directory exists; the next writer removes it recursively, including any partial index, seal and copied files, and reports the discarded ID. After rename the whole image is visible. The fsync ordering makes an acknowledged commit durable on the assumed filesystem; after an unacknowledged crash, recovery accepts a final image only if its seal, schema and tree validation pass. On startup, validate every candidate before selecting it as a base or allowing retention to count it as usable. On-disk corruption after validation is outside the crash-only guarantee; protect the root from independent mutation and use separate integrity monitoring for media damage.

If a final image has a missing, half-written, corrupt or inconsistent index/seal, report its ID and the reason and do not reuse it, expose it through the read wrapper, or count it as a usable retained backup. Under the exclusive GC lock, atomically move it out of `snapshots/` into a quarantine namespace; fsync both parents. Existing compliant readers finish before the move. For diagnosis, walk its `trees/` without following links and derive an inventory of actual paths, types and sizes, reporting walk errors separately. This inventory is **not** a reconstructed source fingerprint or proof that missing files never existed, and must not be installed as a trusted index or published as a complete snapshot. Discard its broken index as authority; keep the quarantined tree and diagnostic inventory for operator inspection, outside retention. If quarantine cannot be completed, stop with an error instead of using or deleting the suspect image. Continue with the newest validated image, or perform a full backup if none is valid. If there are no usable images, do not delete any data; a successful new commit restores a usable snapshot. Quarantine disk usage is reported and requires explicit operator cleanup.

A source that disappears between listing and opening, becomes unreadable, changes observably during copying, or produces a scan error causes the **entire run** to fail. Close handles, release locks and remove its staging tree best-effort; report source ID, relative path, operation and error to stderr, and exit nonzero. No new snapshot appears and existing snapshots remain available. If interrupted cleanup fails, the next run removes the abandoned staging tree. If a directory is absent from the initial scan because it was already deleted before the freeze, it is simply absent from the snapshot; source root absence or inaccessibility is an error. Scheduled and interactive runs have identical semantics and exit codes: 0 committed and retention successful, 1 backup failed, 2 committed but retention failed, 3 commit outcome indeterminate. Logs include the run ID and committed snapshot ID when known.

## Incremental behavior and retention

Unchanged is decided **per file** by the existing `file_state` size and floating-point mtime pair, compared with the source fingerprint saved in the latest validated image. Same-size edits with preserved/restored mtime, or edits hidden by timestamp resolution or floating-point rounding, can be missed; metadata-only changes are also outside the restore contract. Opening the source checks availability but does not detect these edits. Hard-linked unchanged files share immutable backup storage; changed files are copied to new inodes. Never hard-link from a live source. If fingerprints are missing or incompatible, copy that file instead. This is a deliberate speed/integrity tradeoff, not content-level deduplication.

Keep the seven newest valid committed snapshots, including the one just committed. After validation, delete older valid images only under the exclusive GC lock, one tree at a time, and stop on error. Never delete the newest valid image; if validation or enumeration is uncertain, stop rather than delete. The last usable snapshot therefore survives even if a run or deletion fails. A crash during deletion may leave a partially removed final tree: before deleting, atomically rename each victim into a private `trash/` namespace under the exclusive GC lock and fsync both parent directories; only then recursively delete it. A later writer finishes trash cleanup under the exclusive GC lock. Trash is never listed as snapshots and is safe to remove because all prior compliant readers drained before the rename. Retention waits for readers instead of unlinking an image they are using.

## Performance and scaling budget

For an initial backup of **1 GiB in 50,000 files**, set an acceptance budget of **60 seconds elapsed** on a local SSD, with all source writers already quiescent, no competing I/O or lock wait, and at least 2 GiB free on the backup filesystem. This is a derived planning budget, not a measurement or a guarantee on arbitrary hardware. Assumptions to verify on the deployment machine: sustained copy throughput at least 100 MiB/s (10.24 s); at most 50,000 file operations at an aggregate 0.4 ms per file for listing, opens, metadata, creation and closing (20 s); at most 50,000 file fsyncs at an amortized 0.3 ms each (15 s); index serialization, directory fsyncs and fixed overhead at most 5 s; plus 9.76 s margin. Total: 10.24 + 20 + 15 + 5 + 9.76 = **60 s**. These are explicit aggregate workload allowances, not independent hardware guarantees; run an end-to-end cold-cache benchmark with the actual directory shape and durability settings and revise the budget or hardware if it fails. Directory-heavy trees, slower fsync, contention, validation and lock waits can exceed it. Do not claim existing `synccli.copy_file` achieves this: its full-file read and lack of fsync differ from the planned copier.

Let N be source count, F the total file count, D the total directory count, B the total source bytes, P the total bytes in all relative path strings, C the bytes in new/changed files, and R the number of published snapshots before retention. Let Fᵢ, Dᵢ and Pᵢ be the corresponding values for published image i. Per successful run, scanning and change detection take O(N + F + D + P), assembling takes O(F + D + P), and validating all published images takes O(Σᵢ(Fᵢ + Dᵢ + Pᵢ)); sorted traversal may add O(F log F) comparisons. Copy I/O is O(C), with O(F) source opens and up to O(F) hard links. First run has C = B. Process validation one image at a time: per-run memory is O(N + F + D + P + maxᵢ(Fᵢ + Dᵢ + Pᵢ)) for sorted scans and manifest maps, plus a fixed 1 MiB copy buffer; no whole-file buffer. Work across all directories is summed, not multiplied by N. Lock count is N source locks plus two root locks; a single run has at most one copy stream, independent of N.

With R = 7, published logical tree size is at most 7B if each image has at most B bytes; physical file data is at most the sum of distinct copied file versions across those seven images, bounded by 7B, plus filesystem metadata and index/path storage O(7(F + D + P)) when each image has at most F files, D directories and P path bytes. A new complete staging image adds at most B data bytes and O(F + D + P) metadata, so normal peak before GC is at most 8B data bytes and O(8(F + D + P)) metadata under those same size assumptions. Hard links reduce physical bytes, not logical image size or inode/directory-entry work. Actual images may differ in size: use the sum of their individual B, F, D and P values instead of the equal-size bound. Failed cleanup, quarantine, trash, filesystem allocation overhead, and external open handles can add space beyond these normal-operation bounds; report cleanup failures and available space rather than assuming retention guarantees a fixed disk ceiling.

## Verification plan

Keep `python3 -m unittest` passing for the existing API. Add backup integration tests using temporary roots: first and incremental runs, unchanged inode reuse and changed/deleted files, hidden and empty directories, multiple source IDs, unsupported types, and the documented same-size/same-mtime limitation. Inject failures at scan, open, copy, fsync, index write, rename and deletion boundaries, including process termination, then restart and assert that readers see only validated complete images and staging/trash cleanup progresses. Corrupt and truncate both staged and committed indexes, test inventory/quarantine and fallback, and assert a rebuilt inventory is never trusted as an index. Exercise two writers and a long-lived reader in separate processes, including retention waiting for the reader, source-writer locking, and lock release on death. Run the stated 1 GiB/50,000-file benchmark on the target filesystem with fsync enabled and record the hardware, tree shape, timing and result.
