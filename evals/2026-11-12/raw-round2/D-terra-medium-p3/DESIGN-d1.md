# backupctl design

## Contract and operating assumptions

One invocation snapshots the **entire configured set** of N named source directories as one generation. A generation is either published in full or not published at all. The configuration supplies unique, stable source IDs, absolute source paths, a backup root, and a source-barrier lock path. IDs cannot contain path separators, `.` or `..`; roots cannot overlap one another or the backup root. Configuration errors abort before publication. A successful snapshot contains regular files, including dotfiles and files in dot-directories, and empty directories. Symlinks and special files are rejected with a path-specific error, rather than followed or silently omitted. File bytes, mode, and mtime are recorded; ownership, ACLs, extended attributes and hardlink relationships within the source are not promised.

A genuine point-in-time image across several live trees cannot be manufactured by walking them sequentially. Every process that changes these trees must take the source barrier **exclusive** for its whole mutation; backupctl holds it **shared** from before enumeration until all copies and validation are finished. An OS/filesystem snapshot mounted read-only for all configured roots is an alternative implementation of this same frozen-view contract. Writers that bypass the barrier, filesystem corruption, and external mutation of backup files are outside the consistency guarantee. Backupctl still detects and aborts on the observable disappearance, unreadability, or changes described below. The source barrier is separate from the backup locks so restore readers do not block source writers.

Supported deployment is a single host with a local filesystem supporting POSIX advisory `flock`, same-filesystem atomic directory rename, hardlinks, and directory `fsync`. All backup writers, retention tools, and restore readers must follow the lock protocol below. Locks use fixed, permanently existing files outside snapshot directories and are never unlinked; kernel releases them on process death. No correctness claim is made for independent hosts or filesystems with different locking/rename semantics. Backup storage is private to the backup service; published files are immutable and readers open them read-only. In particular a restore **copies** data rather than hardlinking or modifying it. Uncooperative tools which directly delete or modify backup files are not supported.

## Layout and publication

```text
backup-root/
  .writer.lock                 # one backup/maintenance writer
  .readers.lock                # retention/readers handshake
  .work-<random>/              # private incomplete generation
  .cache/                      # disposable derived indexes
  snap-00000000000000000001/   # published generation
    index.json
    trees/<source-id>/<relative-path>
```

The fixed-width 20-digit sequence gives lexical and chronological order, as required by `snaputil.list_snapshots` (`snaputil.py:8-20`); allocate one greater than the largest published sequence while holding the writer lock. Always retain the highest-numbered published generation, even if externally damaged, until a higher one is published; hence deleting older generations cannot cause sequence reuse. Refuse sequence overflow. Staging and final names are on the same filesystem; only a complete generation ever has a `snap-` name. IDs are encoded/validated and all stored relative paths must be normalized, non-absolute, free of `..`, and resolved without following symlinks. `snaputil.safe_snapshot_path` (`snaputil.py:54-63`) does **not** enforce its docstring: absolute paths override the prefix and `..` can escape it. Fix that function with strict validation and containment checks, and use directory-relative, no-follow operations when traversing untrusted paths; do not rely on the current implementation.

Run procedure:

1. Acquire `.writer.lock` exclusively, waiting by default; scheduler and interactive invocations use the same path, code and outcomes. Create lock files securely if needed without replacing existing inodes. Under this lock clean abandoned `.work-*` and temporary cache files from earlier writers; report cleanup failures and stop if safe cleanup is impossible. A second run cannot clean an active first run's staging tree.
2. Select the newest usable published generation as a baseline; verify its index structure and its relationship to the tree as described below. Take the source barrier shared. Scan all roots and build the candidate file and directory lists. Any scan, stat or permission error aborts the whole run.
3. Create a fresh private staging tree. For each regular file, compare its source state against the baseline. For an unchanged file, open and verify the source is readable and still has the expected state, then hardlink the **backup's** baseline file into staging. For a changed or new file, stream-copy into a new staging file with bounded buffers, preserving the captured mode and nanosecond mtime. Never link to the live source. Check opened file identity and state against the scan both before and after the operation, and verify the path still names that file. A mismatch, short read, source or destination error, failed metadata operation, or failed hardlink aborts the generation; no partially copied file becomes published. Do not silently fall back on a failed hardlink: report the error. The barrier supplies the actual stable-view guarantee; these checks catch observable violations, not every possible undisciplined write.
4. Build `index.json` from **successfully materialized** staging entries, including source IDs, relative paths, directories, file size, source mtime and mode, actual backup inode mtime and mode, schema version and generation ID. Keep source and backup metadata distinct: an unchanged hardlink can retain an earlier inode mode or nanosecond mtime even when source metadata differs. Validate that entries and tree agree using the recorded backup metadata, with no extras or missing objects. Write the index to a temporary file inside staging, flush and `fsync` it, rename to `index.json`, then `fsync` the staging directory. Flush and `fsync` new file contents and metadata and bottom-up created directories before publishing. Release the source barrier after the image is complete. Atomically rename the staging directory to its final `snap-...` name and `fsync` the backup root. This rename is the visibility/commit point: a reader sees either no generation or the entire tree and index together. No `latest` pointer is needed.
5. Report the generation, copied and reused counts, and errors; only after successful publication consider retention. An abort returns nonzero, reports the source ID/path and operation, removes staging if possible, and leaves all prior generations untouched. Ctrl-C follows the same rule; an uncatchable kill leaves only private work for the next run. Scheduler and human get identical exit status and diagnostics. A missing or unreadable file means **no new snapshot at all**, never an index entry for a missing file or an implicit carry-forward of the old version. Previously published snapshots remain usable.

The `fsync` ordering makes publication durable to the extent provided by the supported filesystem; the core guarantee is for process interruption. If rename succeeds but a subsequent `fsync` or reporting fails, report an indeterminate outcome including the generation ID; the next run discovers the already published complete generation. Do not retry publication under that ID or delete it on that error.

## Index, recovery, and existing code

The per-generation `index.json` is part of the immutable image, not a mutable global pointer. A separate `.cache/` index may accelerate baseline selection, but is derived and never authoritative. Write cache updates with a temporary file, file `fsync`, atomic rename, and directory `fsync`. At startup discard an incomplete, unparsable, wrong-version, wrong-generation, or structurally invalid cache, report the reason, and reconstruct it from the selected published tree and its validated index. Traverse the tree to verify every indexed path, type, size and recorded backup mtime and find extras; never invent an entry for a missing file. The tree alone cannot recover the source metadata of a reused inode: recover those fields from the valid published index. If that index is corrupt, the generation is unusable as a baseline rather than guessing source state. This validation is metadata-based, not a content checksum or bit-rot detection.

A dead writer's incomplete or corrupt staging index is discarded with the entire `.work-*` tree, never repaired and published. For a published index that is missing, malformed, or inconsistent with the tree (e.g. external damage), report the generation as damaged and do not use or advertise it as a valid baseline. Do not rewrite it in place while readers may be using it. Continue from the next newest validated generation, or do a full backup if none is valid. Quarantine/removal of damaged generations is allowed only under the reader-exclusion protocol and must not remove the last usable generation. If a reader has already selected externally damaged data, the protocol cannot retroactively make it valid; the normal crash protocol prevents creation of such a published index in the first place.

Ground implementation in the existing modules, with explicit changes:

* Adapt `synccli.scan_files` (`synccli.py:10-19`) for the scan: its current `os.walk` prunes dot-directories and silently ignores walk errors, so add inclusion of hidden directories, strict `onerror`, file-type checks, and directory enumeration. Preserve deterministic relative paths. Its current return of files alone cannot represent empty directories.
* Reuse `synccli.file_state` (`synccli.py:22-25`) for the established size/mtime comparison, and adapt `synccli.build_manifest` (`synccli.py:28-33`) to collect the extra fields and directory entries and surface races/errors. Capture nanosecond mtime for preservation and mode separately; the change predicate remains the existing size and floating-point mtime pair.
* Use `synccli.changed_files` (`synccli.py:36-42`) per source ID to identify new or changed files. Paths absent from the new scan are absent from the new tree; `changed_files` alone does not calculate deletions. A fresh staging tree avoids `synccli.sync`'s in-place destination behavior (`synccli.py:72-87`), which cannot publish an atomic image.
* Refactor `synccli.copy_file` (`synccli.py:62-69`) into a streaming, checked copy primitive: the current implementation reads the whole file into memory, opens the destination directly and suppresses all `OSError`s. Return success only after complete copy and propagate errors. Replace `synccli.sync`'s direct manifest write (`synccli.py:85-86`), which currently writes the scanned source manifest even after a failed copy, with the staging/index/rename protocol above. Existing synccli users and tests should retain their documented behavior except where explicitly updated and tested.
* Use `snaputil.list_snapshots` (`snaputil.py:8-20`) to enumerate generations, then strictly filter/validate names and indexes. Its actual implementation accepts **any** directory starting `snap-`, not just the documented pattern. Reuse/refactor `snaputil.prune_snapshots` (`snaputil.py:23-36`) to accept the validated explicit deletion set and a caller-held exclusion lock; its current unconditional `rmtree` cannot be used safely against live readers, and `keep=0` can delete everything. `snaputil.snapshot_disk_usage` (`snaputil.py:39-51`) can report logical bytes per snapshot, but counts hardlinked bytes again for every snapshot and is not physical allocation. Do not use `snaputil.is_stale` (`snaputil.py:66-73`) for reader liveness: it only compares directory mtimes, and its `<=` contradicts its own equality claim.

Change detection is **per file**, by exact equality of `file_state`'s `(size, st_mtime)` values, not by content. Same-size edits with restored/coarsely rounded mtimes can be missed; mode-only edits also do not trigger a content copy. The index must nevertheless capture the current mode and nanosecond mtime, and restore applies those indexed values to its own newly copied file rather than modifying the hardlinked snapshot inode. If stronger detection is required, a future content-hash policy must explicitly change this contract. The source barrier prevents normal concurrent edits but cannot fix metadata collisions between runs.

## Readers and retention

A restore, listing operation that will subsequently traverse a snapshot, or person inspecting files takes `.readers.lock` shared **before** listing/selecting a generation and holds it through the last read/close. Provide a `backupctl read`/restore wrapper to acquire this lock for a command, and document that direct traversal without it is unsupported. Atomic publication needs no reader lock: existing generations are immutable and a new name appears only after completion. Advisory locks cannot protect an arbitrary reader that does not participate; requiring this protocol is essential for safe deletion.

Keep the newest 14 usable generations, including the just-published one. Under `.writer.lock`, retention attempts `.readers.lock` exclusive **nonblocking**. If any reader is active, skip the entire prune and report it; a later run retries, so a long restore does not block backups. With exclusive reader lock held, re-list and validate, choose only generations older than the newest 14 usable ones, and delete them oldest first. Never remove the newest usable generation or the highest-numbered published generation, even if configured retention is invalid or validation/deletion fails. Deletion errors are reported and stop pruning; the newly published snapshot remains successful but the command returns a distinct nonzero maintenance status. To prevent a crash during deletion from leaving a partially removed `snap-*` directory, while still holding exclusive reader lock first atomically rename each victim to `.trash-<sequence>` and `fsync` the root, then recursively delete it. Thus readers never discover partial deletion. A future writer cleans `.trash-*` under the writer lock; a reader already using that generation could not have been present at the rename. Do not expose trash through snapshot listing. Retention never starts before a complete replacement is committed.

## Scaling and budget

Let N be source count, F the maximum total file count of the current tree or any examined generation, D the corresponding maximum directory count, P the maximum total bytes in their relative path strings, B the current logical source bytes, C changed/new bytes, U unchanged file count, K=14 and R the number of published generations. One run scans/stat-checks O(N+F+D) entries, sorts O(F log F) in the existing scanner, validates a baseline in O(F+D+P), and copies C bytes plus O(U) hardlink operations; the initial run has C=B. Index read/write is O(F+D+P) plus serialized metadata. Rebuilding the disposable cache costs another O(F+D+P). In the worst case, validation for baseline fallback and retention examines all R generations: O(R*(F+D+P)) work and O(R log R) name sorting, plus deletion of their entries. With the existing list/dictionary-based helpers, processing one generation at a time gives peak memory O(F+D+P+N+R) plus a fixed 1 MiB copy buffer, rather than O(B); per-file index/state constants are implementation-dependent. Peak open descriptors are bounded by a fixed small implementation limit, e.g. 16, because work is sequential. The number of fixed backup locks is 2 regardless of N.

The retained logical view has up to K*B bytes if generations are each at most B bytes, although shared hardlinks save physical file data: physical payload is at most B for the first generation plus the sum of changed/new file sizes in later retained generations, excluding filesystem allocation granularity and metadata. In the worst case every file changes, so payload is at most K*B for retained generations plus B for one in-progress generation; metadata/index and directory entries add O((K+1)*(F+D+P)). Actual allocated blocks, compression and sparse-file behavior are filesystem-dependent. When a reader prevents pruning or deletion fails, there is **no fixed disk cap**: with R published and T trash generations of at most B bytes, payload is at most (R+T+1)*B plus O((R+T+1)*(F+D+P)) metadata, and R can grow with successful runs. A reused inode has at most R+T+1 links including staging, absent external links; account for filesystem hardlink limits and report a failed link rather than corrupting a generation. On insufficient space abort staging and preserve previous generations; do not delete the last snapshot to make room.

Initial-backup performance budget: **260 seconds** for 1,000,000,000 bytes across 30,000 files, on a specified reference local storage setup. This is a conditional engineering target derived from the following serial-service assumptions, not a measured result: effective 100 MB/s source reads and destination writes (10 s each), 2 ms per file for listing/stat/open/create/metadata work (60 s), 4 ms average per file for durable file flush (120 s), and 7 s for directory flushes, index serialization and publication. Total 207 s; 25% contingency gives 258.75 s, rounded up to 260 s. Assume the effective throughput includes the underlying device contention; cold cache, slower fsync, antivirus, huge directory counts, or a slower device may exceed the target. For other workloads use `1.25*(B/read_rate + B/write_rate + F*(entry_latency + fsync_latency) + directory_index_time)`. Benchmark the actual implementation on the target filesystem with this fixture, including flushes and publication, and report wall time and assumptions before claiming the target is met. Incremental runs still read directory metadata and validate U source files; hardlink reuse avoids re-copying unchanged payload bytes.

## Verification plan

Retain `python3 -m unittest` for existing behavior (the six current tests pass). Add integration tests for hidden and empty directories; full and incremental generations, hardlink reuse, changed/deleted files and mode-only changes; same-size/mtime collision as a documented limitation; inaccessible/disappearing files at scan and copy; corrupt/partial staging and disposable cache recovery; malformed or tree-inconsistent published index fallback; and strict path/symlink rejection. Inject failures and kill a subprocess at each copy, index flush, rename and deletion boundary, then verify every visible generation has a matching tree/index and a later run progresses. Run overlapping backup processes and a long-lived shared-lock restore: verify serialized writers, successful publication during restore, skipped prune, and safe later prune. Test crash after victim rename and before trash cleanup, failed deletion, disk-full, and last-usable-generation preservation. Finally run the 1 GB/30,000-file benchmark on the target filesystem with fsync enabled and record observed time separately from the derived budget.
