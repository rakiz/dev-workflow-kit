# backupctl design

## Contract and operating assumptions

`backupctl run --config CONFIG` takes one atomic backup of the entire configured set, not one independently published backup per directory. The configuration maps stable, unique, single-component IDs to absolute source directories and specifies a backup root and a retention count, default 7 and minimum 1. A scheduler and an interactive invocation use the same command, behavior, output and exit codes. The backup root must not be inside any source; reject overlapping sources and duplicate IDs. Reject a root that is a symlink or cannot meet the filesystem requirements below. Configuration changes affect the next snapshot; each snapshot records its own mapping.

A genuine point-in-time image of multiple actively changing trees cannot be obtained by walking them sequentially. The source provider is therefore part of the contract: it must supply immutable, stable views of *all* configured roots representing the same logical instant. For example, the evals workflow pauses writers across all roots, creates read-only filesystem snapshots of the relevant volumes while paused, then releases writers and supplies those views. A single volume snapshot covering all roots also works. The views remain mounted and immutable until the run finishes. If the provider cannot establish this contract, fail before publication; do not silently fall back to a live scan. The provider must clean up views even after a crash, or make its own view cleanup idempotent on the next run. This requirement is independent of backupctl's locks: they do not stop source writers.

Use a local POSIX filesystem for the backup root with same-filesystem atomic directory rename, hard links, advisory `flock`, and working file and directory `fsync`. Reject unsupported or failed operations rather than weakening the contract; do not claim these semantics for arbitrary network filesystems. The root and its parent must be controlled by the backup operator, not mutated by uncoordinated processes. Snapshots and their file contents are immutable after publication. Readers must follow the lease protocol below, and neither readers nor operators may edit files in a snapshot: hard-linked snapshots can share inodes. Read-only permissions are helpful but are not an enforcement mechanism against the owner or root. The design protects against process interruption and, with the specified sync ordering and a filesystem honoring it, power loss; it cannot protect against hardware corruption or dishonest storage.

## On-disk format and reader contract

```text
backup-root/
  .writer.lock                 # stable inode, never replace or unlink
  .readers.lock                # stable inode, never replace or unlink
  .work-<random>/              # unpublished; ignored by readers
  .trash-<random>/             # retired; ignored by readers
  snap-00000000000000000001/
    tree/<source-id>/...       # regular files, directories and symlinks
    index.json                 # version, config, entries and source states
    seal.json                  # version and digest of canonical index
```

Snapshot names use a fixed-width, monotonically increasing sequence allocated under the writer lock from the highest published name, with overflow a hard error. Abandoned work consumes no visible name. Since pruning always retains the newest snapshot, this remains monotonic; do not select a name already present. The backup root is on one filesystem, so `.work-*` to `snap-*` is a same-directory atomic rename. Published names are the *only* snapshots. A snapshot index describes exactly the tree in that same directory, including empty directories and symlinks. It lists each path's type, file size, nanosecond mtime and content SHA-256 for regular files, symlink target, and directory metadata; it also records source IDs and configuration. Encode paths reversibly, including non-UTF-8 POSIX names, use a versioned canonical serialization, and reject duplicates, invalid components and conflicting path types. Store the source size/mtime state used for change detection; preserve the corresponding mtime on the backed-up file so it can be re-derived. Index and seal are outside `tree`, so source names cannot collide with them.

Every restore, human browsing session, listing tool that will subsequently open files, and pruning operation must cooperate: open the persistent `.readers.lock`, take a shared lock **before** listing/selecting a snapshot, retain it until all tree and index accesses are finished, then release it. Reader-facing backupctl commands validate the selected index against its seal and tree before exposing it, and reject a corrupt snapshot; restore integrations must do likewise. A reader sees either no new name or the entire new snapshot; it never consults a run-in-progress flag. A restore may run concurrently with snapshot creation and publication. A shared lock also prevents repair or deletion of its selected snapshot. Provide `backupctl list` and `backupctl with-snapshot NAME -- COMMAND` as convenient lease-holding interfaces; the latter holds the lock for the command and its complete access lifetime. Restore integrations must acquire the same lock themselves. A bare filesystem browser or existing `snaputil` CLI does not implement this protocol: if any reader cannot cooperate, disable repair and pruning while that reader may be active. There is no safe automatic deletion of a directory while arbitrary uncooperative readers may traverse it.

## Building and publishing a run

1. Open and exclusively lock `.writer.lock` for the whole run, including recovery and retention. Colliding runs wait; a killed process releases the OS lock. Validate configuration and source-view contract. Run startup recovery as described below, then select the newest valid published snapshot as the reuse base. Hold a shared reader lease while accessing that base, releasing it before acquiring the exclusive lease for pruning. The writer lock prevents another backupctl writer from pruning it.
2. Create a unique `.work-*` directory under the root. Scan the stable views and build a candidate manifest, including all directories, regular files and symlinks, with paths relative to their configured IDs. Never follow symlinks during scanning, copying, recovery or tree traversal; preserve the link text itself. Reject sockets, devices, FIFOs and other unsupported types with a path-specific error. Validate paths and use descriptor-relative, no-follow operations when traversing the source and stage; do not allow `..`, absolute components or symlink traversal to escape either root.
3. For each regular file, compare source state with the prior snapshot's entry for the same source ID and relative path, only if that ID still maps to the same configured source path; otherwise treat it as new. For an unchanged file, hard-link the prior immutable snapshot file into the stage and carry forward its digest. For a changed/new file, stream it from the view into a newly created stage file, computing SHA-256 and setting recorded mtime. Verify the opened file is a regular file and its size and mtime match the scanned state before and after the copy; also verify the copied byte count. Re-stat/open even reuse candidates so a missing or unreadable source is an error. Create directories and symlinks afresh, preserve their recorded metadata where supported, and omit paths absent from the source view. Set recorded directory mtimes bottom-up after all children are created, so index reconstruction sees the intended values. Never write or chmod a hard-linked file, including during metadata setup. Do not copy special files or dereference source symlinks. All failures, including failed stat, directory enumeration, open, read, write, link, metadata setting, or verification, abort the *entire* run.
4. Construct the final canonical index from entries actually staged, and validate its paths, types and size/mtime against the stage. Its content digests come from streamed copies or the validated previous index; source-view immutability and snapshot immutability are required for these to be meaningful. Write `index.json` and `seal.json` inside the stage; the seal contains SHA-256 of the entire canonical index. The seal is independent of the index and is retained for recovery, not an authentication mechanism. Flush and `fsync` every new data file, index and seal; sync created directories bottom-up, then sync the stage directory. Hard-linked data was already synced when first published. Any sync failure aborts publication.
5. Rename the fully prepared stage to the next `snap-*` name and `fsync` the backup root. This rename is the visibility/commit point; nothing modifies the published tree afterward. A crash before it leaves only an ignored stage; a crash after it leaves a complete snapshot, even if the command cannot report success. If root `fsync` fails after rename, report an indeterminate durability result and exit nonzero; do not remove or rewrite the published snapshot. On restart inspect it as a published candidate. Then apply retention. Report the published name, counts of copied/reused files and bytes, and any cleanup failure.

If a listed file disappears or becomes unreadable at any point it is needed, or any directory cannot be read, the run publishes **no** snapshot and reports the path, operation and error on stderr with a nonzero exit; the preceding snapshot remains usable. No old version is silently substituted, and no partial index is published. This is the same for scheduled and manual runs. The private stage is removed best-effort immediately and otherwise on the next run. If a file disappeared only after it was successfully read from an immutable view, the view contract has been violated: abort when that violation is detected; a provider that cannot guarantee immutability is not supported.

Change detection is per regular file, using `(size, mtime_ns)` from the stable view, rather than a whole-directory timestamp. It misses content edits that preserve both values, including deliberate mtime restoration and filesystem timestamp-resolution collisions. The SHA-256 stored in the index verifies the copied image; it does not detect such source edits on the fast reuse path. Operators needing stronger detection must use an optional full source-content hash comparison, at the cost of reading all source bytes each run. Metadata changes other than size and mtime do not cause file content recopy; directory/link metadata are recreated each run. Document precisely which metadata is restored: file content, type, mtime, directory structure and symlink target; ownership, ACLs, xattrs and permissions are outside this version's contract.

## Recovery and integrity

On startup, with the writer lock held, remove abandoned `.work-*` and `.trash-*` trees, then sync the root. Cleanup is idempotent; if removal fails, report the path and fail the run rather than accumulate unbounded abandoned trees. Never treat these names as snapshots. A process killed during cleanup can retry it. A valid published snapshot has a parseable supported index and seal, matching canonical index digest, valid relative paths and a tree matching the indexed types, sizes and mtimes. Check these before using a snapshot as the base; content hashes can be verified by a full scrub. Index corruption discovered on an older snapshot is handled in the same way when it is encountered or explicitly scrubbed.

If an index is missing, truncated, malformed, or fails the seal digest, take the **exclusive** reader lock while holding the writer lock, waiting for existing readers and blocking new ones. Re-scan that snapshot's tree without following links and re-derive its canonical entries, including file hashes and preserved metadata. Reconstruct the index using the configuration and format data independently stored in `seal.json`; the seal therefore includes the source ID/config mapping and format version as well as the expected index digest. Only if the reconstructed canonical index hashes to the sealed digest is it proven to be the original indexed image. Write a temporary index within the snapshot, fsync it, atomically replace `index.json`, fsync the snapshot directory, and report the repair and snapshot name. A crash during repair leaves either the old index or the complete replacement; the next run repeats the procedure. Readers are excluded until the replacement is durable. Metadata required to reconstruct the index must be restricted to values recoverable from the tree or seal; no transient copy counters belong in it.

If the seal is missing, corrupt or unsupported, the reconstruction digest differs, or the tree is damaged, do not invent an index or claim a repaired snapshot: report it as invalid and leave it intact for diagnosis. The sealed digest prevents silently accepting a tree with missing or altered files when the index is lost, assuming SHA-256 collision resistance and an intact seal. The seal itself is not redundant against its own damage. Never delete or overwrite the last usable snapshot; if none can be validated, preserve all candidates and fail with an actionable diagnostic. A previously valid snapshot can suffer external corruption between checks; hardware damage and uncoordinated edits are outside the publication guarantee. If a bad snapshot cannot be repaired, exclude it from base selection and retention accounting; never silently present it as valid through backupctl. If recovery cannot safely complete, fail the run rather than expose a knowingly corrupt index to new backupctl readers. A complete scrub hashes all contents to discover silent data corruption; the normal fast validation checks metadata and the index seal, not file contents.

## Retention and concurrent readers

After successful publication retain the newest `K` valid snapshots, with `K >= 1`. Invalid snapshots are preserved separately for diagnosis and do not count as usable. Under the writer lock, release any shared reader lease, then acquire the exclusive `.readers.lock`; this waits for every cooperating restore or browser to finish and prevents new ones from selecting a victim. Recheck the valid list and keep at least the newest valid snapshot. Atomically rename each eligible old snapshot to a unique `.trash-*` name, sync the root, and only then recursively delete the trash and sync the root again. A crash during deletion leaves only an ignored trash tree, cleaned at startup. The exclusive lease is held until retirement is complete; it may be released after all victims are renamed because no existing reader remains and new readers cannot select trash. A failure to acquire a lease or to delete trash is reported as a retention/cleanup failure, never as deletion of the newest usable snapshot. Publication may have succeeded even when retention fails; report both facts and return nonzero. No deletion takes place without reader cooperation; if such cooperation is unavailable, explicitly disable retention and accept unbounded storage growth.

## Grounding in the existing code

Implement `backupctl.py` beside the existing modules, reusing and extending their functions rather than calling `sync()` on the final destination:

* `synccli.scan_files` (`synccli.py:10–19`) performs sorted relative-path enumeration. Extend it, or add a strict mode to it, to include hidden directories, surface `os.walk` errors, retain directory entries (including empty ones), and use no-follow traversal/type handling. Its current hidden-directory filtering and filename-only result are insufficient.
* `synccli.file_state` (`synccli.py:22–25`) provides size/mtime state. Extend it with no-follow regular-file checks and `st_mtime_ns`; the current floating-point mtime loses precision. `synccli.build_manifest` (`synccli.py:28–33`) composes scan and state: extend it for strict error handling, all supported types, source IDs and the richer index. `synccli.changed_files` (`synccli.py:36–42`) already compares each new state with the old; use it for the regular-file size/mtime comparison, filtering out non-state fields such as hashes and handling removed entries by constructing a fresh tree.
* `synccli.copy_file` (`synccli.py:62–69`) currently reads an entire file into memory and swallows every `OSError`, possibly leaving a partial destination. Extend/replace its copy implementation with the streaming, hashing, verification, fsync and propagated-error contract above. Do not use `synccli.sync` (`synccli.py:72–87`) as the transaction: it updates a destination in place and writes its manifest directly even when copying silently failed. Its existing manifest is neither a commit record nor crash-safe. Retain the existing synccli behavior for its callers through explicit new options or a new strict helper, and test both interfaces.
* `snaputil.list_snapshots` (`snaputil.py:8–20`) supplies sorted `snap-` directory names. Our fixed-width sequence names sort in commit order, and our private prefixes are ignored. Validate entries as real directories without following symlinks and validate their contents before treating them as usable: the helper only checks a prefix and follows directory symlinks. Use `snaputil.snapshot_disk_usage` (`snaputil.py:39–51`) only for a labeled **logical** per-snapshot size; it double-counts shared hard links and follows symlinks, so adapt it to no-follow traversal before using it. Physical usage requires inode-deduplicated accounting.
* Reuse the retention selection logic in `snaputil.prune_snapshots` (`snaputil.py:23–36`) by factoring selection from deletion or adding a guarded callback. Do not invoke its current direct `shutil.rmtree`: it has no reader lease, no rename-to-trash, and accepts `keep=0`. Reuse `snaputil.safe_snapshot_path` (`snaputil.py:54–63`) only after strict path and snapshot-name validation and no-follow traversal; its `normpath` plus `join` does **not** prevent absolute paths, `..` escape or symlink escape. Never rely on its current docstring as a safety guarantee. Do not use `snaputil.is_stale` (`snaputil.py:66–73`) as a completion or lock signal: its `<=` implementation also contradicts its equality docstring.

## Cost and performance budget

Let N be source directories, F total entries, B total regular-file bytes, P total bytes in their encoded relative paths and metadata, C changed/new regular-file bytes, R changed/new regular-file count, D total directories, K retention count, and S the number of published plus abandoned/invalid snapshots actually present. Normal scanning and comparison cost O(N + F log F + P), including the existing sorted scan; payload work is O(C) reads and writes plus O(F) metadata/link operations. First run has C = B and R equal to all regular files. Full hashing/scrubbing or index reconstruction costs O(B) reads for the snapshot involved. Directory creation and per-snapshot indexes cost O(F + P) each even when no file content changes. N changes the cost through its entries plus O(N) configuration work, not an exponential factor.

With a 1 MiB streaming buffer, in-memory scan, old/new manifests and sorted paths cost O(N + F + P) plus 1 MiB of payload buffer, rather than O(size of largest file). This is an asymptotic upper bound, not a byte-precise Python heap promise. Root listing/selection costs O(S log S) time and O(S) names. With successful retention, valid published snapshots are at most K after a run and at most K+1 during publication; invalid snapshots are deliberately preserved and add to S without a fixed bound. Physical payload storage after retention is at most the sum of unique file-version sizes across retained snapshots, bounded by the sum of their logical B values; hard links save unchanged versions. Add O(sum of F + P over retained snapshots) for directory entries and indexes, and up to one in-progress stage's new payload C and metadata. Trash consumes space until removed; cleanup failures stop subsequent runs and require resolution. Logical `snapshot_disk_usage` is not physical allocation.

**Initial-backup budget:** target at most 120 seconds for 1 GiB, 30,000 regular files and 4,000 directories on a reference local filesystem, conditional on the following explicitly testable service rates: combined source-read/destination-write throughput at least 80 MiB/s; aggregate scan/stat cost at most 0.30 ms per file; create/write/finalize including file fsync at most 1.5 ms per file excluding payload transfer; directory creation and fsync at most 1 ms per directory; hashing throughput at least 300 MiB/s; and at most 10 seconds total for index serialization, source-view setup, root sync and fixed overhead. Conservatively add rather than overlap: `1024/80 + 30000*0.00030 + 30000*0.0015 + 4000*0.001 + 1024/300 + 10 = 84.2 s`, leaving about 35.8 s headroom. These are assumptions, not measurements or a guarantee on slower disks; verify them with a representative cold-cache run and report observed elapsed time, tree shape, hardware/filesystem and whether view setup is included. Per-file fsync latency, not just bandwidth, can dominate. A failed view provider, slow storage, large directories or longer syncs invalidate the budget.

## Verification before shipping

Keep `python3 -m unittest` passing and add meaningful tests using isolated temporary roots: initial snapshot and incremental reuse/change/deletion; hidden files, empty directories, links and path escape rejection; source disappearance/unreadability and enumeration errors with no publication; injected failures at copy, index write, fsync, rename and each recovery step; malformed index repaired from a matching seal and rejected on mismatched tree or damaged seal; writer collisions and a reader holding a lease across publication and attempted pruning; kill/restart at each phase; hard-link immutability; and retention of at least one usable snapshot. Exercise source-view creation and the reader protocol with actual workflow/restore integration, not just mocks. Run the stated performance workload on the target filesystem and compare the recorded times with the budget assumptions.
