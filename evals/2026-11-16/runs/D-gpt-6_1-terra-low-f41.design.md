# backupctl design

## Contract and operating assumptions

`backupctl run --config CONFIG` publishes one snapshot containing all configured roots, or publishes none. The scheduler and an interactive invocation use the same command, exit codes, and reporting. Configuration assigns each root a unique, stable, path-safe ID; IDs, not source absolute paths, name the top-level trees in a snapshot. Reject overlapping source roots, a backup root within any source, duplicate IDs, and a backup root that cannot provide the filesystem operations below.

A genuine point-in-time image of multiple actively changing trees cannot be obtained by walking and copying them sequentially. A configured source-view provider must supply a **single consistent read-only view of all roots** at one instant: for example, an atomic filesystem consistency-group snapshot, or an application quiesce held while all filesystem snapshots are acquired. The provider reports the capture instant and releases the view after copying. If it cannot provide this contract, fail before publication; an ordinary live walk is not a fallback. The provider and its setup are deployment requirements, not functionality supplied by `synccli`. Disappearance, read errors, or a violated view contract still fail the run as described below.

The backup root must be on one local filesystem supporting atomic same-filesystem directory rename, hard links, advisory locks released on process death, and file and directory `fsync`; validate capabilities and fail closed otherwise. All snapshot access and retention must follow the reader protocol below. Backup files and directories are owned by the backup service and must not be modified by other processes. These assumptions are essential: uncoordinated path-based readers cannot be protected from concurrent recursive deletion by POSIX rename or open file descriptors alone. Likewise, no software-only design can promise a point-in-time multi-root view of arbitrary live writers without a cooperating source-view mechanism.

Snapshot contents include regular files, directories including empty and hidden directories, and symlinks as symlinks; never follow symlinks when scanning or restoring. Store file bytes, mode and mtime, directory mode/mtime, and symlink target. Devices, sockets, FIFOs, unsupported metadata such as ACLs/xattrs, or a path that cannot be represented safely cause the run to fail and be reported. Hard links in sources need not be preserved as links in the image. Backups and restores must not follow symlink ancestors; paths are relative components, reject absolute paths, empty components, `.` and `..`, and use directory-relative no-follow operations. Restore must additionally handle symlink targets as data, not traverse them.

## Layout and publication

```text
backup-root/
  .writer.lock                 # stable lock file, never replaced
  .locks/<snapshot-id>.lock    # stable per-snapshot reader/pruner lock
  .allocation                  # atomically replaced durable ID state
  .staging/<unique-run-id>/    # never listed as a snapshot
  .trash/<snapshot-id>/        # unpublished, interrupted deletion
  snap-YYYYMMDD-HHMMSS-<20-digit-sequence>/
    trees/<root-id>/...
    index.json
```

Under the exclusive writer lock, allocate a monotonically increasing sequence in `.allocation`, using temp-file write, file `fsync`, atomic replace and parent `fsync` before use. The timestamp is a logical UTC timestamp at least as large as the last allocated timestamp, even if the clock moves backwards. Fixed-width sequence makes `snaputil.list_snapshots()`'s lexical sorting (`snaputil.py:8-20`) match allocation order. Gaps from crashes are fine. Never reuse IDs, including after pruning. Validate allocation state; if corrupt, recover a sequence and timestamp greater than all IDs in published, trash, staging, and permanent lock names, report recovery, and durably persist it before allocating. Create and sync the ID's permanent lock file before publishing; include its name in recovery even after deletion. If these records cannot establish a safe high-water mark, fail rather than risk reuse. Lock files remain permanently named by ID, including after deletion, so a lock inode cannot be replaced under a reader.

1. Acquire exclusive `.writer.lock` for the whole run, including recovery and retention. A second run waits, then obtains a fresh source view and bases its decisions on the latest published snapshot. A killed process releases the OS lock; never break a lock using a PID or timeout. When reading or repairing the previous snapshot, the writer also follows the per-snapshot locking protocol; the writer lock alone does not exclude readers.
2. Clean abandoned `.staging` trees and finish deleting `.trash` trees, with no active writer. Neither location is visible through `list_snapshots`. Acquire a consistent source view, allocate an ID and build the entire image in a unique staging directory on the backup filesystem.
3. Generate `index.json` from entries **actually created**, with schema/version, snapshot ID, source-view capture time, root IDs, and canonical relative paths, types, sizes, mtimes, modes and symlink targets. The same index serves as the prior source-state manifest for the next run. Write it to a temporary file, validate its schema and correspondence to the staged tree, flush and `fsync` it, rename to `index.json`, and `fsync` its directory. No index may advertise a file whose copy failed.
4. Flush and `fsync` newly written file data and relevant metadata; `fsync` the completed directories bottom-up, including staging and its parent. Atomically rename the staging directory to its final `snap-*` name and `fsync` the backup root. The rename is the visibility/commit point: before it, no snapshot is listed; afterwards, readers see the whole immutable tree and index. No committed content is ever edited in place. A crash before commit leaves disposable staging; after commit it leaves a complete snapshot, even if the run did not print success. Power-loss durability requires the stated filesystem `fsync` guarantees. If a post-rename sync fails, report an indeterminate commit and the ID; the next run checks what survived rather than claiming failure means no snapshot exists.
5. Release the source view. Apply retention only after successful publication; report its results separately. A failure before commit removes staging when possible, releases the view and exits nonzero; the next run cleans any remainder. Failure after commit does not roll back a complete snapshot.

Each snapshot is independently restorable: it contains every selected tree entry, not a chain of deltas. Unchanged regular files can share immutable inodes with a previous snapshot via hard links; deleting an older name does not remove bytes still linked by newer snapshots. Never write, chmod, or utime a linked file after linking. If hard linking fails, copy that file to a fresh inode and report the fallback; errors in that copy abort the run. Restrict write access to all snapshot trees, since modifying any hard-linked inode would change multiple snapshots.

## Grounding and change detection

The following are implementation reuse points, including necessary changes to existing behavior:

* Refactor `synccli.scan_files(root)` (`synccli.py:10-19`) into a reusable deterministic walker for the frozen view. It currently skips dot-prefixed directories and `os.walk` silently ignores traversal errors; backup's variant must include hidden directories, record empty directories and symlinks without following them, and raise/report traversal errors. Do not rely on its existing file-only result as a complete tree.
* Refactor `synccli.build_manifest(root)` (`synccli.py:28-33`) to consume that walker and expose per-entry errors and non-file types. Reuse `synccli.file_state(path)` (`synccli.py:22-25`) for regular-file size and mtime, and extend the record with type and mode. Retain its exact size/mtime representation in the persisted index so that re-derived records compare identically. Capture symlink and directory metadata separately without following links.
* Feed old and new maps to `synccli.changed_files(old_manifest, new_manifest)` (`synccli.py:36-42`); it compares complete values for each new path. Use the same path/type/size/mtime/mode representation for regular files. For entries absent from the new manifest, do not link or copy anything into the new tree: `changed_files` does not report deletions. Compare directory and symlink records as well, creating them afresh as necessary.
* Replace/refactor `synccli.copy_file` (`synccli.py:62-69`): it reads the entire file into memory, opens the destination directly, and suppresses **all** `OSError`s, including destination failures. A backup copy instead streams in fixed 1 MiB chunks to a new staged file, propagates every read/write/close error, applies mode and mtime to the new inode, and syncs it before publication. Verify the copied byte count and file metadata against the frozen-view record. Reuse its parent-directory creation intent, not its silent-error or whole-file-read behavior.
* Do not call `synccli.sync` (`synccli.py:72-87`) as the transaction: it writes directly into a mutable destination, loads JSON without recovery, and writes the source manifest even when `copy_file` silently failed. The backup transaction wraps the refactored scanning, state, comparison and copy primitives above with staging and atomic publication.
* Reuse `snaputil.list_snapshots` for committed candidates and its sorting; validate each returned entry as a real non-symlink snapshot directory with a valid ID before using it. It actually accepts any `snap-` directory, despite its narrower docstring. `snaputil.prune_snapshots` (`snaputil.py:23-36`) cannot be called unchanged: it directly `rmtree`s visible snapshots without reader locks and `keep=0` deletes all. Refactor it to use the retention selection and locked unpublish/delete protocol below, with `keep >= 1`. `snapshot_disk_usage` (`snaputil.py:39-51`) can report **logical** bytes, not deduplicated physical usage, because hard-linked files are counted for each snapshot. Its `os.stat` follows symlinks, so adapt it to use no-follow traversal before using it for these trees.
* Fix `snaputil.safe_snapshot_path` (`snaputil.py:54-63`) before using it: `normpath` does not contain `..` or absolute inputs, and the existing join can escape the snapshot. Reject unsafe components and use no-follow directory-relative traversal, not string normalization alone. Do not use `snaputil.is_stale` (`snaputil.py:66-73`) for safety or retention: it uses `<=` despite claiming equality is not stale, and mtime does not establish reader liveness.

An unchanged regular file is one with the same relative path, type, size, floating-point `st_mtime` and mode as the latest usable snapshot. This is a **per-file metadata** test, not a content hash: edits that preserve size and mtime (including edits hidden by timestamp precision or restored timestamps) and mode can be missed. This is an explicit limitation of reusing `file_state`; use a content-hash policy in a future change if that tradeoff is unacceptable. A renamed file is new and is copied. A previously omitted file cannot be silently retained: this design never commits an incomplete snapshot.

## Failure, index recovery, and reporting

On a missing, unreadable, or changing/unverifiable source entry at scan, stat, open, read or verification, abort the **entire** run. No new snapshot is published and the previous one remains usable. Report the root ID, relative path, operation and error to stderr, release the view, and exit nonzero; scheduler and person get identical behavior. This also applies to an unreadable root or directory; never interpret an `os.walk` error as an empty directory. A missing entry genuinely absent from the consistent view is simply absent from the new snapshot. Destination, index, space, and sync errors are also fatal before publication. Exit 0 means published and retention completed, 1 means no confirmed publication, and 2 means publication succeeded or may have succeeded but a post-commit operation failed; include the ID and status in the report. Log counts of copied, linked, removed-from-new-image, and failed entries.

The authoritative data is the immutable published tree, not a shared mutable global index. There is one self-contained index per snapshot. Before trusting a prior index, parse and validate its version, ID, paths, types and structure and check it against the snapshot tree. On a malformed, truncated, missing, or tree-inconsistent index, report the snapshot ID and error; discard only that index, not its tree. Under that snapshot's exclusive reader lock, re-scan the tree using the adapted walker and state functions, re-derive the entry map and atomically replace `index.json` via a synced temp file and directory `fsync`. File mtimes and modes were preserved on fresh copies, so the file-state keys are reconstructible; directory and link metadata are re-derived as stored. Persist capture metadata separately in a small synced `capture.json` at publication and validate it during recovery; if it is missing or corrupt, mark capture time unknown rather than inventing it. Snapshot ID and root IDs are re-derived from the snapshot name and tree. The index is an inventory of the data actually present, not proof against undetected external content corruption. Validate the rebuilt index against the tree before using it. If the tree cannot be scanned or represented, mark that snapshot unusable for this run, report it and try older snapshots; if none is usable, do a full backup. Never prune the only known usable snapshot.

`capture.json` is metadata alongside `index.json`, not part of `trees`; it is written and synced before publication. Index repair is the sole permitted modification to a published snapshot and occurs atomically while its exclusive reader lock is held. Remove stray index temp files under that lock. An interrupted repair leaves either the old index or the complete replacement; retry recovery on the next access. Readers use the same validation/recovery gate before consuming an index. The guarantees assume no independent actor mutates backup data or bypasses that gate; an externally corrupted index discovered before recovery cannot itself be made valid retroactively.

## Reader and retention protocol

Restore tooling and human inspection use a provided `backupctl` reader API/command: choose a published ID, open its stable `.locks/<ID>.lock`, acquire a **shared** lock, then recheck that the snapshot still exists and is published. If not, release and retry selection. Hold the lock across index validation/recovery and the entire traversal/copy, then release it. If recovery is required, drop the shared lock, acquire exclusive, recheck existence and validity, repair if needed, then retry with a shared lock; do not upgrade in place. A reader that dies releases its lock automatically. Existing separate restore tooling must adopt this protocol; direct shell readers must run inside a `backupctl with-snapshot ID -- COMMAND` wrapper which holds the shared lock for the command's lifetime. Commands must not leave detached descendants reading after the wrapper exits.

Default retention is the newest 30 **usable** snapshots, configurable to an integer `keep >= 1`. Run it under the writer lock after a successful publication. Validate candidate snapshots and never delete the newest usable one; if usability cannot be established, skip deletion and report it. For each older candidate, acquire its exclusive lock **nonblocking**. If busy, skip and report deferred deletion; future runs retry. After acquiring it, recheck eligibility and existence, atomically rename `snap-ID` into `.trash/ID`, fsync both parents, and recursively remove it while holding the lock. A reader racing selection either acquired its shared lock first, preventing deletion, or acquires it after unpublication and fails the existence recheck. The newest usable snapshot remains visible throughout. A crash after rename leaves an invisible trash tree; the next writer finishes cleanup. If a reader cannot or will not cooperate, retention must be disabled while it might be reading; there is no safe way to infer its absence from directory timestamps. Retention failure or deferred deletion is reported, not silently treated as completed.

## Performance and scaling budget

Initial-backup target: **at most 90 seconds** for 1 GiB and 30,000 regular files, under these explicit deployment conditions, not a measured result or a guarantee on arbitrary hardware:

* Aggregate end-to-end streamed source-read plus destination-write rate at least 100 MiB/s: 1,024 / 100 = 10.24 s.
* All per-file scanning, stat, open/close, directory work, manifest serialization and validation average at most 2 ms/file: 30,000 × 0.002 = 60 s.
* All file and directory syncs together at most 10 s; consistent-view acquisition at most 1 s; remaining fixed setup, rename, release and reporting at most 8 s.

The deliberately serial upper-budget sum is **89.24 s**. Qualify an installation by measuring these components on its actual source, destination and provider; cold cache, small-file sync cost, encryption, or a slower device may violate the assumptions. The initial run does not hash file contents. The copier's bounded chunks avoid `copy_file`'s largest-file-sized allocation. A benchmark should include creation, complete validation, syncing and publication, not just data transfer.

Let N be roots, F the total entries in their frozen trees, Fprev the prior tree's entries, B their regular-file bytes, P the total bytes in relative paths and link targets, L the maximum path length, C changed/new regular-file bytes, Z unchanged bytes copied after link failures, U unchanged regular files, K the retention count, H the lifetime count of allocated snapshot IDs, and Q the total entries of all published snapshots examined for retention/validation. One run scans the source and validates the prior tree in O(N + F + Fprev + P) work apart from sorting and copies C + Z bytes, with Z at most B − C; the first run copies B bytes. Sorting costs O(F log F × L) worst-case path-comparison work. It creates O(F) directory entries and at most U hard links, so unchanged bytes are not recopied when links succeed, although unchanged metadata work is still linear. Retention candidate validation/deletion adds O(Q plus entries removed), including their path-processing and sorting costs, and listing/sorting S published names costs O(S log S); deferred readers can make S exceed K.

Peak process memory is O(N + F + Fprev + P + Pprev + S) for current and prior manifests and sorted paths, plus a fixed 1 MiB copy buffer; candidate snapshots are validated one at a time, so include the largest candidate's entry/path footprint if larger than the prior image. No allocation scales with the largest file's bytes. With R successfully retained snapshots plus one in-flight staging tree, physical regular-file data is at most the sum of their copied file sizes, bounded by (R + 1) × Bmax when each image has at most Bmax bytes; hard links reduce this toward one copy of each version but do not guarantee savings. Metadata and directory/index storage is O(sum of F + P across those R + 1 images), plus O(H) permanent small lock files and constant allocation/writer state. Trash left by a crash or deletion failures adds the size of those undeleted trees; busy readers, repeated failures, and unbounded history mean there is no fixed disk cap. The 30-snapshot policy limits successfully pruned snapshots only when readers release locks and deletion succeeds.

## Verification plan

Keep `python3 -m unittest` passing for the existing sync behavior, and add tests for the refactored primitives and backup transaction: hidden/empty directories and symlinks; first copy, unchanged link reuse, deletion and metadata-only changes; same-size/same-mtime limitation; missing and unreadable sources and destination errors; corrupt/truncated index and interrupted repair; two concurrent writers; reader versus pruning and reader/pruner selection races; and hard-link fallback. Inject process termination at each staging, index-write, rename, fsync and trash-delete boundary, restart, and assert that every listed snapshot is complete and restorable and at least one usable snapshot remains. Test clock rollback, ID allocation recovery, unsafe paths and rejected unsupported files. Exercise an actual consistent-view provider while sources are concurrently modified, then benchmark the 1 GiB/30,000-file workload against the stated conditions.
